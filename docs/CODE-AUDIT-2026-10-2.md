## 🔴 P0

### 1. Токены Telegram-бота и VK лежат в `/settings`, а `/settings` читается без авторизации

**Что найдено.** `database.rules.json:57-58`:

```json
"settings": {
  ".read": true,
```

Правило unconditional — любой неаутентифицированный запрос из интернета читает
всё под `/settings`. При этом клиент пишет туда **живые учётные данные**:

| Куда | Что | Где в коде |
|---|---|---|
| `settings/telegram` | `groupToken`, `channelToken`, `botToken`, `chatId`, `groupId`, `channelId` | `js/admin-channels.js:57`, `:88`, `:115` |
| `settings/vk` | `token` (VK access token), `peerId` | `js/admin-channels.js:174`, `:218` |

Читает их обратно не только админка, но и **страница игрока**:
`js/official-alerts.js:164` (`settings/telegram`) и `:328` (`settings/vk`) —
вызов судьи/маршала отправляется прямо из браузера игрока через
`fetch('https://api.telegram.org/bot' + token + '/sendMessage')`
(`js/official-alerts.js:75`, `:126`) и `https://api.vk.com/method/messages.send`
(`:236`).

**Последствия.** Telegram Bot Token — это полный контроль над ботом:
`getUpdates` даёт историю переписки судейского чата, `sendMessage` — рассылку от
имени клуба, `setWebhook` — перехват всех последующих сообщений. VK access token
даёт доступ к API с теми scope, с которыми выпущен.

Сузить доступ потомка в RTDB нельзя — это ограничение платформы, и оно уже
известно команде: ровно по этой причине мастер-пароль убрали из `settings`
в Secret Manager (`functions/index.js`, комментарий к
`MASTER_PASSWORD_HASH_SECRET`: «этот узел публичен (RTDB не позволяет сузить
доступ потомку)»). Токены каналов — тот же класс проблемы, в том же файле правил,
но их не перенесли.

Дополнительно те же токены дублируются в `localStorage` админского устройства
(6 ключей: `pestovo_tg_group_token`, `pestovo_tg_bot_token`,
`pestovo_tg_channel_token`, `pestovo_tg_group_id`, `pestovo_tg_channel_id`,
`pestovo_vk_token`) — читаются любым скриптом на origins и остаются на общем
планшете после смены администратора.

**Замер.** 5 мест записи токенов в `/settings`, 2 места чтения с клиента,
1 правило `.read: true` (`grep -n "settings/telegram\|settings/vk" js/`).

> ⚠️ **Что не проверено.** Из этой песочницы нет доступа к
> `livescore-b77e4-default-rtdb.firebaseio.com`, поэтому факт, что токены уже
> лежат на проде, по сети не подтверждён. Проверка одной командой с любой
> машины: `curl https://livescore-b77e4-default-rtdb.firebaseio.com/settings.json`.

**Как чинить.** Отправка в Telegram/VK должна уйти на сервер — триггер
`onAlertCreated` (`functions/index.js`) уже существует и уже рассылает Web Push
по той же записи в `/alerts`. Токены — в Secret Manager или в ветку с
`.read`/`.write` только для админа. После этого `settings/telegram` и
`settings/vk` удаляются, токены в `localStorage` — тоже.

> **Статус (1.122.0 → 1.123.0).** Выполнено частично и сознательно:
> - 1.122.0: токены переехали в `channels/` с `.read` только для админа/мастера,
>   `settings/telegram|vk` разрешено лишь удалять, ключи в `localStorage`
>   вычищаются (`purgeChannelSecretsFromStorage`), доставку перенесли
>   в `onAlertCreated`. Находка закрыта полностью.
> - 1.123.0: заказчик отказался от зависимости от Cloud Functions — вызов
>   обязан уходить из браузера игрока. Браузер не может отправить сообщение,
>   не прочитав токен, поэтому `channels/.read` ослаблен до `auth != null`.
>   **Это частичный откат находки:** интернет без авторизации токен
>   по-прежнему не видит, но видит любой вошедший, включая анонимную
>   QR-сессию. Решение принято заказчиком явно; компенсации (отдельный бот
>   только для уведомлений, ключ ВК с правом «Сообщения», отсутствие токенов
>   в `localStorage` и логах, `.write` только админский, переключатель
>   `settings/alert_delivery_mode` обратно на `server`) описаны
>   в `docs/release-1.123.0.md` §2 и показаны админу в панели «Вызовы 🚨».
>   Пункты про `localStorage` и `/settings` остаются закрытыми.

### 2. `/markers` и `/reactions`: запись разрешена любому вошедшему, на всю ветку

`database.rules.json:171-173`:

```json
"markers": {
  ".read": "auth != null",
  ".write": "auth != null",
```

`database.rules.json:186-188`:

```json
"reactions": {
  ".read": true,
  ".write": "auth != null"
}
```

`.write` на самой ветке означает, что любой аутентифицированный клиент может
перезаписать или удалить **любую** запись в поддереве — а не только свою.
Дочерний `.validate` (`markers/$rid/$pid/$hole`, строка 177) ограничивает только
тип и диапазон значения и для удаления (`null`) не срабатывает:
`!newData.exists()` даёт `true`.

Это не теоретический доступ: QR-карточка без личного аккаунда получает
анонимную Firebase-сессию (`js/firebase-config.js`, `auth.signInAnonymously()`
для `scorer.html` / `marker.html` / `setup-round.html`), то есть
`auth != null` выполняется у любого, кто отсканировал QR. Для сравнения:
у `rounds`, `tournaments`, `protocols`, `users`, `usersPublic`, `broadcasts`,
`markerAssignments` запись ограничена админом/мастером/владельцем.

`markers/` при этом — живая read-модель: её читают `js/marker.js:106` и
`js/scorer.js:137`, в неё пишет `js/live.js:1729` и fallback-путь
`js/score-write.js:62,66`.

**Как чинить.** Убрать `.write` с ветки и выдать его на уровне
`$rid/$pid/$hole` (владелец записи / её маркер / админ), как сделано для
`rounds/$rid/players/$pid`.

| auth / design-preview / handicap / marker / scorer / stats | 26 | 23 |

23–25 отдельных `Listen`-запросов на одну страницу — ради значений вроде
`settings/tn_gender_split`, `settings/hcp_badge_variant`,
`settings/stats_display_variant`. Источник —
`initPestovoDisplaySettings()` (`js/utils.js:10416-10431`, цикл по
`PESTOVO_DISPLAY_CONFIGS`) и `pestovoBindView5()` (`js/utils.js:6800-6811`) —
каждый ключ получает собственную подписку.

**Порядок исправления важен.** Соблазнительное решение — одна подписка на
`/settings` вместо 23 — сейчас **неприменимо**: `/settings` содержит токены
(находка 1), и общая подписка разослала бы их на каждую страницу, включая
публичные. Сначала секреты уезжают из `/settings`, потом подписки
схлопываются в одну.

Отдельно: Firebase SDK мультиплексирует одинаковые пути в один `Listen`,
поэтому дубли `rounds×4` на `index.html` — это не 4 загрузки дерева, а 4
колбэка-рендера на одно обновление. Трафик дублирует находка 4, не эта.

### 7. Каждая запись счёта пишет аудиторские события дважды

В `functions/score-audit.js` доставка в защищённый индекс выполняется из двух
мест без всякой защиты от повторного входа:

1. `scoreWrite` после транзакции сам читает outbox и вызывает `deliver()` —
   `functions/score-audit.js:133-134`;
2. транзакция создаёт `_scoreAuditOutbox[requestId]` (строка 126), на что
   срабатывает триггер `onScoreAuditOutbox` (`:142-144`) и вызывает `deliver()`
   **со снапшотом из аргумента** — то есть даже если outbox уже удалён.

`deliver()` (`:30-38`) делает по одному `set()` на каждое событие. Итог:
пачка из N операций стоит 2N записей в `scoreAudit/` вместо N, и оба пути
пишут одни и те же ключи. То же для `studioScoreWrite` (`:179` + `:183`).

Идемпотентность результата не страдает (ключи совпадают), страдает стоимость и
латентность: лишняя серия записей на каждое сохранение лунки.

### 8. `purgeScoreAudit` раз в сутки выкачивает всю базу в память одной функции

`functions/score-audit.js:222` и `:228`:

```js
const owners = (await db.ref(collection).once('value')).val() || {};   // rounds, затем tournaments
...

```

Три полных чтения дерева за прогон: все раунды со всеми игроками и счетами, все

игры это единицы мегабайт в одном `once()` — плюс счётчик прочитанных байт на
каждом прогоне.

Замеры подписок RTDB и времени рендера выполнялись отдельным harness'ом поверх
Playwright с записывающей заглушкой Firebase: она сохраняет колбэки `.on()` по
путям, после чего в страницу подаётся синтетический снимок `/rounds` и
замеряется время каждого колбэка. Скрипты harness'а в репозиторий не кладутся —
это разовый измерительный инструмент, а не проверка; если замер нужно
превратить в регрессионный тест, его стоит оформить как `tools/check-*.js`
в стиле существующих браузерных проверок.
