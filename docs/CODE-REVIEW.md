## 1. Архитектура и модульность — ВЫСОКИЙ приоритет

**Проблема.** Код — классический «global script» без ES-модулей, сборщика и
корневого `package.json`. Каждый файл кладёт функции в глобальную область
видимости (`var` на верхнем уровне создаёт `window.*`, см. комментарий в
`js/firebase-config.js:9-21`). В `utils.js` **530** глобальных функций, в
`admin.js` — **357**.

Последствия:
- Невозможно tree-shaking, ленивая загрузка, переиспользование в Node/tests.
- Конфликты имён при росте (уже проявляется — см. раздел 2).
- Функции `utils.js` жёстко связаны с глобальными `db` / `currentUser`
  (`js/utils.js:514`, `:1843`, `:1859`) — чистая логика смешана с Firebase.

**Что сделано правильно (опереться на это).** `js/tn-engine.js` — эталонный
UMD-модуль («чистая доменная логика, без DOM и Firebase», `js/tn-engine.js:1-46`),
работает и в браузере (`window.TnEngine`), и в Node (`module.exports`). Это
образец для остального кода.

**Предложения.**
1. Ввести корневой `package.json` + сборщик (Vite/esbuild). Мигрировать
   скрипты на ES-модули (`import`/`export`). Разбить гигантские файлы по
   ответственности (см. раздел 3).
2. Выделить слой «сервисов» (Firebase-access) отображения: `db`, `auth`,
   `currentUser` инжектить через аргументы/контекст, как в `tn-engine`,
   чтобы логика была тестируема без браузера.
3. Не ломать существующий `var`-на-window подход резко — мигрировать
   постранично, начиная с утилит, на которые есть тесты (`tn-engine`).

## 2. Дублирование кода — ВЫСОКИЙ приоритет

Одни и те же функции переопределяются в разных файлах (копипаста между
страницами, т.к. каждая HTML грузит свой набор скриптов):

| Функция | Где определена (раз) |
|---|---|
| `onAuthReady` | `admin.js:195`, `live.js:100`, `app.js:19`, `tournaments.js:2` (+ ещё ~9 мест через проверку `typeof onAuthReady`) |
| `callOfficial` | `live.js:1984`, `marker.js:270`, `scorer.js:426` |
| `buildHoles` | 3 места |
| `renderHole` / `updDisp` | по 2 места |
| `qrUrl` / `loadTournaments` / `isScoreKioskUrl` / `checkVerify` / `applyScoreKiosk` | по 2 места |

Это «расходимость»: правка логики в одном месте забывается в другом
(реальный баг-вектор, а не только запах).

**Предложения.**
- Вынесть общие хелперы (`onAuthReady`/`navAuth`, `callOfficial`, `qrUrl`,
  `loadTournaments`, проверки kiosk) в один модуль `js/common/` и импортировать.
- `onAuthReady` заменить на централизованный диспетчер авторизации (шина
  событий), чтобы страницы подписывались, а не переопределяли глобальную ф-ю.

## 4. Безопасность — КРИТИЧНО / ВЫСОКО

### 4.1 XSS через `innerHTML` (риск КРИТИЧНО → ВЫСОКО)
`escapeHtml` определён корректно и экранирует `& < > " '`
(`js/utils.js:241`). **Но применение — opt-in на каждом месте вставки**, и
есть ~90 `innerHTML`-присваиваний со «словами-полями» без `escapeHtml` на той
же строке. Уязвимые пути с пользовательскими данными:
- `js/marker.js:178-179` — имена/счёт игрока и маркера в `innerHTML` (без
  экранирования на строке).
- `js/admin.js:3234`, `:3349`, `:3398` — `fgSettingsHtml(... players ...)`
  вставляет имена участников; экранирование внутри `fgSettingsHtml`
  (опр. `admin.js:3167`) не прослеживается — нужен аудит.
- Резервный паттерн `typeof escapeHtml === 'function' ? escapeHtml(x) : x`
  (`js/feed.js:29`, `js/stats.js:69`, `js/tn-scorecard.js:32`) сегодня
  безопасен (ф-я всегда загружена), но хрупок: стоит убрать ветку-«как есть».

Данные (имена игроков, анонсы, алерты) приходят из Firebase **без
серверной санитизации** (см. 4.3), поэтому любая забытая экранизация =
stored XSS.

**Предложения.**
- Safe-by-default: вместо `el.innerHTML = '<b>'+x+'</b>'+y` — центральный
  билдер `html\`...\`` (tagged template), авто-экранирующий интерполяции, либо
  обязательный `textContent` для чистого текста.
- Подключить **DOMPurify** для тех мест, где собирается HTML из многих кусков
  (feed, admin-превью).
- Добавить **Content-Security-Policy** (script-src, style-src, connect-src к
  firebaseio.com) — предотвратит большинство инъекций даже при ошибке
  экранирования.
- Аудит `fgSettingsHtml` и `marker.js` на предмет экранирования имён.

### 4.2 `firebaseConfig.apiKey` в клиенте (НЕ уязвимость, но уточнить)
`js/firebase-config.js:2` содержит web API key. Для Firebase Web SDK это
**норма** (ключ не секретный); защита доступа — в security rules. Тем не менее
стоит вынести конфиг в `.env`/build-переменную, чтобы не коммитить
project-specific значения, и явно задокументировать, что защита — в rules.

### 4.3 Нет Firebase security rules в репозитории (ВЫСОКО)
В репозитории **нет** `database.rules.json` / `firestore.rules`. Вся
авторизация и валидация полагается на клиент. Cloud Functions тоже почти не
валидируют вход (`functions/index.js` читает `b.title/b.body`,
`a.hole/a.playerName/a.type` «как есть», без проверки прав/длины/типа — см.
`onBroadcastCreated`, `onAlertCreated`).

**Предложения.**
- Добавить и коммитить `database.rules.json` с: (a) чтением публичных веток
  (`/settings/*`, `/broadcasts`, `/leaderboard*`) и закрытием приватных;
  (b) записью `/broadcasts`, `/alerts` только для `isAdmin` (проверка
  `auth.uid` → `users/$uid/admin === true`); (c) `/rounds/$rid/players/$uid`
  доступно владельцу; (d) `.validate` на типы/длины полей.
- В Cloud Functions добавить минимальную валидацию (типы, длина title/body ≤
  N, корректность `audience.uids`, `a.type ∈ {referee,marshal}`).

## 5. Тестирование и качество — СРЕДНИЙ приоритет

Есть ~40 файлов `tools/test-*.js` (хорошо, что они есть!), но:
- Нет единого раннера: каждый запускается вручную `node tools/test-x.js`.
- Нет assertion-библиотеки (самописные `eq`/`check`), нет `npm test`.
- Нет CI (`.github` отсутствует) — регрессии не ловятся автоматически.
- `package-lock.json` в `.gitignore` → невоспроизводимые зависимости
  (`functions/`).

**Предложения.**
- Корневой `package.json` с `"test": "node tools/run-all-tests.js"` и
  простым раннером, собирающим `tools/test-*.js`.
- Подключить `node:test` (или vitest) + `assert` — убрать самописные
  хелперы.
- GitHub Actions: на push/PR — lint + тесты + деплой functions.
- Убрать `package-lock.json` из `.gitignore` (или задокументировать причину).

## 6. Производительность и утечки — СРЕДНИЙ приоритет

- **Firebase-слушатели:** 37 `.on()` против 5 `.off()`. В `js/live.js:834`
  `roundViewHandler` подписан через `.on('value', ...)`; в `live.js:2020`
  `child_added` на `/users/$uid/notifications`. В многостраничном приложении
  (полная перезагрузка между страницами) это частично смягчается, но внутри
  `live.js`/`solo.js` стоит явно `.off()` при размонтировании/смене раунда,
  иначе — дублирующие срабатывания и утечки при переходах внутри страницы.
- **Service Worker кэш:** `CACHE_NAME = 'pestovo-v1.79.0'` захардкожен
  (`sw.js:1`), версии ассетов проставляются вручную (`?v=NN`, ~12 мест в
  `sw.js`). Забытая «бампнуть» версия = пользователи на старом кэше.
  **Предложение:** генерировать precache-манифест с хешем сборки на этапе
  build (revved filenames), а `CACHE_NAME` выводить из версии релиза.
- **Пересчёты лидерборда:** `live.js` (2 287 строк) перестраивает
  представление на каждое `value`/`child_*` событие. Стоит профилировать
  «горячие» пути и добавить debounce/throttle + memoization для тяжёлых
  вычислений (net-скор, stableford) на больших турнирах.

## 7. Конфигурация курса захардкожена — НИЗКИЙ/СРЕДНИЙ

`HOLES`, `TOTAL_PAR`, `TIMINGS`, `COURSE_RATINGS`, `TEES` жёстко вшиты в
`js/utils.js:5-29`. Для другого поля/клуба код непригоден, а редактирование
«логики» рядом с данными курса — антипаттерн.

**Предложение.** Вынести в конфигурацию (JSON в БД `/settings/course` или
отдельный `js/course.config.js`), загружаемый при старте; `utils.js` держит
только логику доступа (`holePar(h)` и т.п.), а не данные.

## 8. Быстрые победы (quick wins)

1. Добавить `Content-Security-Policy` meta/header — дешево, закрывает класс
   XSS-уязвимостей.
2. Централизовать `onAuthReady` → шина событий (убрать 13 дубликатов).
3. Убрать fallback `: x` в паттерне `typeof escapeHtml ... ? ... : x` →
   всегда экранировать.
4. Добавить `database.rules.json` с проверкой `isAdmin` для `/broadcasts`,
   `/alerts`.
5. Корневой `package.json` + `npm test` раннер тестов + базовый CI.
6. Документировать, что `firebaseConfig.apiKey` — не секрет (в README/ASSISTANT).
