# Firebase Realtime Database — Security Rules

Файл `database.rules.json` — **черновик** правил безопасности, реализующий
принцип наименьших привилегий с проверкой `isAdmin`.

> ⚠️ **ВАЖНО ПЕРЕД ДЕПЛОЕМ**
> В репозитории ранее не было файла правил. Live-правила уже задеплоены в
> Firebase, но их содержимое неизвестно. **Перед применением:**
> 1. Экспортируйте текущие правила (`firebase database:instances:...` или
>    через Firebase Console → Realtime Database → Rules) и сохраните бэкап.
> 2. Сверьте этот файл со схемой ваших данных и правами админа.
> 3. Задеплойте только после проверки на staging / через тест.
>
> Неправильные правила могут сломать работающий сайт или, наоборот,
> открыть данные.

## Что реализовано

- `.read`/`.write` по умолчанию — `auth != null` (залогиненный пользователь).
  Это базовая линия: она НЕ делает данные публичными, но позволяет
  авторизованным пользователям работать с узлами, не перечисленными ниже.
  **Рекомендация:** после инвентаризации всех узлов БД сузить до
  конкретных путей.
- `isAdmin` — инлайн-проверка
  `root.child('users').child(auth.uid).child('admin').val() === true`
  (в RTDB нельзя объявить helper-функцию, поэтому выражение повторяется).
  **Проверьте, что у админов действительно выставляется
  `users/$uid/admin === true`.** Если админ-права даются иначе (например,
  только client-side мастер-паролем), эти правила заблокируют админ-запись.
- `broadcasts`, `vapid`, `settings`, `leaderboard`,
  `push_subscriptions` — запись строго ограничена (`isAdmin` или владелец).
- `alerts` создаётся любым авторизованным (вызов судьи/маршала игроком),
  но изменять/удалять чужие вызовы может только админ (`!data.exists() &&
  newData.exists()` — «создать, но не трогать»); читают админ и участники
  раунда (запрос обязан фильтровать по `roundId` через `query.equalTo`,
  правило проверяет участие в этом раунде). Индекс: `.indexOn:
  ["roundId","status"]`.
- `markers` и top-level `markerAssignments` (легаси-зеркала) пишет только
  админ/мастер: клиентские записи счёта идут через Cloud Function
  `scoreWrite` (ADMIN-доступ), прямые записи игрокам не нужны, а открытая
  запись позволяла подменить привязку маркера и чужие отметки.
- `rounds/$rid/players/$pid` — писать может только владелец записи,
  создатель раунда или админ.
- `broadcasts`/`push_subscriptions` — `.validate` ограничивает длину и
  типы полей (защита от огромных/неправильных payload).

## Секреты интеграций: ветка `channels/` (1.122.0 → 1.123.0)

Токен Telegram-бота и access token сообщества ВК лежат в `channels/telegram`
и `channels/vk`. В публичном `/settings` (`.read: true`) их быть не может —
там им место только как удалённым узлам: `settings/telegram` и `settings/vk`
несут `.validate: "!newData.exists()"`, то есть запись запрещена, а старое
значение разрешено стереть (перенос делает `migrateLegacyChannelSecrets()`).

Права на `channels/` менялись дважды, и это важно понимать перед деплоем:

| Версия | `.read` | Кто отправляет вызов |
|---|---|---|
| ≤ 1.121.0 | токены в `/settings`, `.read: true` | браузер (токен читал весь интернет — P0) |
| 1.122.0 | `admin \|\| tournamentMaster` | Cloud Function `onAlertCreated` |
| 1.123.0 | `auth != null` | браузер игрока (режим `client`, по умолчанию) или Cloud Function (режим `server`) |

1.123.0 сознательно возвращает чтение токена любому **вошедшему**
(включая анонимную QR-сессию): заказчику нужна доставка без Cloud Functions,
а браузер не может отправить сообщение, не прочитав токен. Интернет без
авторизации токен по-прежнему не видит, а `.write` остаётся строго админским —
игрок не может подменить токен и увести вызовы в свой чат. Компенсации
(отдельный бот только для уведомлений, ключ ВК с правом «Сообщения», отсутствие
токенов в localStorage и в логах, переключение в режим `server` одним
селектором) описаны в `docs/release-1.123.0.md` и показаны админу прямо в
панели **Вызовы 🚨**.

Режим доставки хранится в `settings/alert_delivery_mode` — узел публичный и
секретов не содержит, поэтому читается и браузером, и функцией. `.validate`
допускает только `'client'` и `'server'`.

### Отчёт о доставке `alerts/$id/delivery`

Отчёт пишет тот, кто реально отправлял:

- режим `server` — Cloud Function (Admin SDK, правила не участвуют);
- режим `client` — браузер игрока, и вот ему правило нужно.

`alerts/$id/delivery/.write` разрешает запись админу, автору вызова
(`createdBy === auth.uid`) и самому игроку (`playerId === auth.uid`).
`createdBy` добавляет `requestOfficialCall` (`js/utils.js`): в QR-сессии
`playerId` — это игрок, а `auth.uid` — анонимная сессия устройства, поэтому
одного `playerId` недостаточно и отчёт молча не сохранился бы.

Подузел намеренно отделён от `alerts/$id/.write`: само правило ветки
«создать, но не трогать чужое», а отчёт о доставке — это изменение уже
созданного вызова. Запись идёт через `update()`, чтобы серверный leaf
`delivery/push` (число уведомлённых админов) не затирался клиентским отчётом
и наоборот. Сбой записи не отменяет доставку: игрок на лунке не должен
страдать от того, что правила не задеплоены.

**Порядок деплоя 1.123.0:** хостинг → `firebase deploy --only database`.
До деплоя правил браузер не сможет прочитать `channels/` и вызовы не уйдут
никуда, поэтому правила — обязательный шаг, а не косметика.

## Чего НЕТ (следующие шаги)

- Валидация составных полей (например, структура `audience` у broadcast).
- Rate-limiting / защита от спама (это уровень Cloud Functions).
- Правила для Storage (если используется) — отдельный `storage.rules`.
- Firestore rules (если используется Firestore вместо RTDB).

## Удаление данных из админки (кнопки очистки)

`.write` в правилах стоит на **дочерних** узлах (`users/$uid`, `rounds/$rid`,
`tournaments/$id`…), поэтому клиент не может удалить ветку целиком: запись в
`/users` или `/rounds` запрещена. Кнопки «Удалить всех игроков и раунды» и
«Удалить все данные» когда-то делали один атомарный мульти-path update по
веткам — сервер проверяет права на каждый путь и отклоняет весь запрос, так
что не удалялось ничего (игроки оставались). Поэтому:

- на ветки `users`, `usersPublic`, `rounds`, `tournaments`, `protocols`,
  `broadcasts`, `alerts` добавлен node-level `.write` для администратора
  (он и так мог писать любой дочерний узел — новых прав нет);
- мастер-сессия (claim `tournamentMaster`) получила на этих ветках
  **только удаление** (`!newData.exists()`): она может очистить данные, но
  не может создавать/править профили и повышать роли;
- клиент дополнительно умеет удалять детей по одному (`users/<uid>`,
  `usersPublic/<uid>`, …) — это работает и на старых, ещё не развёрнутых
  правилах; успешные и неудачные ветки честно перечисляются в тосте;
- Cloud Function `wipeAllData` (Admin SDK, `functions/index.js`) выполняет ту
  же очистку на сервере, где правила не действуют, — админка вызывает её
  первой и откатывается на браузерное удаление, если она не развёрнута.
  Функция доступна только администратору клуба (`users/$uid` `admin: true`
  или `role: 'admin'`) либо мастер-сессии с действующим claim; свой аккаунт
  администратора она сохраняет, чтобы не отобрать доступ к админке.

Настройки (`settings`), шаблоны турниров (`tnTemplates`), черновики
(`tnDrafts`), ключи пушей (`vapid`) и журнал счёта (`scoreAudit`) при очистке
не удаляются: журнал чистит `purgeScoreAudit` по ретеншену, остальное —
конфигурация клуба.

## Известное ограничение: финализация раунда QR-игроком

Ввод счёта QR-игроком турнирного раунда идёт через Cloud Function
`scoreWrite` (сервер проверяет владение карточкой). Но завершение раунда
(`doFinishGroupRound`/`doFinishSolo`) пишет `finishedPlayers`/`status`
напрямую в `rounds/$rid`, а правило раунда разрешает это только создателю,
админу или мастеру. QR-игрок (анонимная сессия, не создатель) получает
отказ записи: счёт сохранён, но раунд не фиксируется как завершённый —
клиент теперь показывает явную ошибку вместо молчаливого проглатывания.
Правильное решение — серверная операция `finish` внутри `scoreWrite`
(атомарно с аудитом), либо отдельное правило для подузла `finishedPlayers`;
это изменение контракта сервера и требует отдельного решения.

## Приватность профилей: users vs usersPublic (2026-09)

`users/$uid` содержит PII (email, phone, history) и читается только:
владельцем (`auth.uid === $uid`), админом (флаг/роль в своём профиле)
или мастером (`tournament-master`). Читать список `users` целиком может
только админ/мастер.

Публичные данные профилей вынесены в `usersPublic/$uid`: имя, пол,
гандикап, tee, флаги гостя/удаления, агрегаты (roundsPlayed, best*),
`phoneLast4` (для подтверждения владельца раунда). Читается всеми
залогиненными. Запись: владелец, админ, мастер. `.validate` запрещает
писать в зеркало email/phone/history/role/admin.

Наполнение зеркала (три механизма):
1. Регистрация пишет `users` + `usersPublic` одним мульти-path update (auth.js).
2. Админка синхронизирует зеркало при каждом изменении users
   (`syncPublicProfilesMirror` в admin-players.js, чанки по 200).
3. Одноразовая миграция `tools/migrate-public-profiles.js` (firebase-admin).

**Порядок деплоя**: код (двойная запись + зеркало) → миграция или одно
открытие админки → новые `database.rules.json`. Если развернуть правила
раньше наполнения, страницы игроков временно останутся без ростера/
автокомплита (в коде есть fallback-ветки, но UX деградирует).

Плеерские страницы (index/players/stats/live/setup-round) читают только
`usersPublic`; админка (admin.html) — полный `users`. Признак: элемент
`#admin-content` на странице.
