# Фоновые push-уведомления (PWA, приложение закрыто)

Клубные анонсы и вызовы судьи/маршала доставляются через стандартный
**Web Push (VAPID)** — работает на Android (Chrome/Edge/Яндекс) и на iOS
после «Поделиться → На экран „Домой“» и запуска установленной PWA.

## Как это устроено

1. Клиент (`js/pwa.js`) после разрешения «Уведомления» подписывает
   `pushManager` на публичный VAPID-ключ и сохраняет подписку в
   `/push_subscriptions/<key>` (endpoint, ключи p256dh/auth, uid, язык,
   признак админа).
2. Cloud Function триггерится при создании записей:
   - `/broadcasts/{id}` → `onBroadcastCreated` — анонс по аудитории
     (`all` — вошедшим игрокам; `all + includePwa` — всем, включая
     гостей; `roster`/`protocol` — только указанным uid);
   - `/alerts/{id}` → `onAlertCreated` — вызов судьи/маршала админам
     (Web Push — всегда; рассылка в Telegram/VK — только в режиме
     `settings/alert_delivery_mode = 'server'`)
     (`users/<uid>`: `admin: true` **или** `role: 'admin'`).
3. Функция (`functions/index.js`, библиотека `web-push`) шифрует payload
   и отправляет его в push-сервис браузера. `sw.js` показывает
   уведомление в обработчике `push`, `notificationclick` открывает нужную
   страницу.
4. VAPID-ключи генерируются автоматически при первом вызове функции
   `vapidSetup`: публичный — в `/settings/vapid_public_key` (читают все),
   приватный — в `/vapid/privateKey` (только сервер).

## Деплой (один раз)

Требуется план Firebase **Blaze**; веб-пуши практически бесплатны при
клубных объёмах.

```bash
npm i -g firebase-tools
firebase login
firebase use livescore-b77e4

cd functions
npm i
firebase deploy --only functions
```

После деплоя в админке: **Анонсы 📢 → «Фоновые пуши» → Создать/проверить
VAPID-ключи**. Кнопка вызовет `vapidSetup`, статус покажет количество
активных подписок устройств.

Если функции задеплоены в регион не `us-central1`, впишите полный URL
функции в поле на той же карточке — он сохранится в
`settings/push_function_url`.

## Правила базы данных (обязательно)

Приватный ключ не должен быть читаем из браузера. В Firebase RTDB Rules:

Минимально необходимое правило — закрыть приватный ключ:

```json
{
  "rules": {
    "vapid": { ".read": false, ".write": false }
  }
}
```

(остальные правила проекта остаются как есть; Cloud Functions работают
через Admin SDK и правила безопасности не применяются к ним). Клиенты
создающие подписки, должны иметь доступ на запись в
`/push_subscriptions/<ключ>` — в текущей открытой конфигурации клуба это
так и есть; при переходе на строгие правила разрешите авторизованным
пользователям запись собственной подписки.

## Кому уходят вызовы судьи/маршала

Признак админа в профиле бывает двух видов, и оба равноправны (так же его
понимают правила базы, `hasAdminPanelAccess` и серверная `wipeAllData`):

```json
{ "users": { "<uid>": { "admin": true } } }
{ "users": { "<uid>": { "role": "admin" } } }
```

`onAlertCreated` собирает подписки через `getAdminSubscriptions()`: профили
`users/<uid>` читаются Admin SDK (правила не мешают), клиентский флаг
`isAdmin` в `/push_subscriptions` — только запасной вариант для записей без
`uid` и для случая, когда профиль прочитать не удалось. Поэтому устаревший
или незаполненный флаг больше не «глушит» вызовы.

Флаг в подписке ставит браузер (`js/pwa.js` → `pestovoPushPatchProfile`) и
явно сбрасывает его у обычного игрока — запись в базе не копит мусор.

Запись подписки создаётся без чтения ветки `/push_subscriptions`: правила
разрешают её читать только админу, поэтому игрок пишет напрямую под ключ
`sub_<хвост endpoint>`. Иначе `PERMISSION_DENIED` на запросе по `endpoint`
отменял сохранение, и фоновых пушей у игрока не было вообще.

## Мастер-выключатель (админка → «Вызовы 🚨»)

`settings/notifications_enabled = false` гасит уведомления у ВСЕХ игроков:
Cloud Function не отправляет пуши, а клиент (`js/pwa.js`) по подписке на ту
же настройку:

- не показывает новые всплывающие уведомления клуба (анонсы и «судья/маршал
  едет к вам»);
- снимает с экрана уже показанные — уведомления клуба помечены классом
  `.t-club` и закрываются сразу после выключения
  (`pestovoDismissClubNotificationToasts`);
- очищает очередь троттлера `pestovoNotifQueue`.

Настройка применяется в реальном времени: перезагрузка страницы не нужна.
Проверяется тестом `tools/test-notifications-off.js`.

## Telegram и ВКонтакте (вызовы судьи/маршала)

Web Push и рассылка в Telegram/VK — две независимые доставки одного вызова:
сбой одной не отменяет другую.

Кто рассылает по каналам, задаёт публичная настройка
`settings/alert_delivery_mode` — переключатель в админке
(**Вызовы 🚨 → «Кто отправляет вызовы»**):

- `client` (по умолчанию, узел может отсутствовать) — сообщение отправляет
  браузер того, кто нажал «Вызвать судью» (`js/official-alerts.js`,
  `pestovoDeliverOfficialCall`). Cloud Functions для этого не нужны вообще;
- `server` — отправляет Cloud Function `onAlertCreated`
  (`functions/index.js`, `deliverOfficialCall`) через Admin SDK.

Второй отправитель всегда молчит, поэтому дублей нет ни в одном из режимов.
Web Push в любом случае отправляет сервер: браузер игрока не может разбудить
телефон судьи, когда страница свёрнута. Если функции не задеплоены, в режиме
`client` не уходит только push — Telegram и ВКонтакте продолжают работать.

Секреты лежат в ветке `channels/` (`channels/telegram`: `groupToken`,
`groupId`, `channelToken`, `channelId`; `channels/vk`: `token`, `peerId`).
Из публичного `/settings` значения переносит `migrateLegacyChannelSecrets()`
в админке; оба отправителя понимают и старые имена полей (`botToken`/`chatId`),
и один бот на группу + канал.

**Доступ к токенам — осознанное решение 1.123.0.** В 1.122.0 ветку читали
только админ и мастер турниров, и доставка работала лишь на сервере. Без
Cloud Functions браузер игрока обязан уметь прочитать токен, поэтому теперь
`channels/.read = "auth != null"`: его видит любой вошедший, включая анонимную
QR-сессию, но по-прежнему не видит интернет без авторизации
(docs/CODE-AUDIT-2026-10-2.md, находка 1 — сознательное ослабление,
подтверждённое заказчиком). Компенсации:

- бот — отдельный, только для уведомлений, добавлен только в группу судей;
- ключ сообщества ВК — с правом «Сообщения», без доступа к данным и стене;
- токены не пишутся в localStorage и не выводятся в консоль;
- запись в `channels/` по-прежнему строго админская: игрок не может подменить
  токен и увести вызовы в свой чат;
- режим `server` полностью убирает токены из браузера, и переключается одним
  селектором, если позиция по секретам изменится.

Форматы запросов разные, и это важно:

- Telegram Bot API — `POST` с `Content-Type: application/json`
  (`chat_id`, `text`, `parse_mode: HTML`);
- VK API из браузера — JSONP `<script>` на
  `https://api.vk.com/method/messages.send` с параметрами в URL
  (`access_token`, `peer_id`, `message`, `random_id`, `v=5.199`, `callback`).
  Для этого в CSP хостинга (`firebase.json`) в `script-src` добавлен
  `https://api.vk.com`: без него браузер блокирует запрос, и доставка молча
  не работает — на dev-сервере vite такого заголовка нет, поэтому локально
  «всё работало»;
- VK API с сервера — `POST` с `Content-Type: application/x-www-form-urlencoded`
  (VK API 5.131). JSON в теле VK **не поддерживает**
  (<https://dev.vk.com/ru/api/api-requests>), ответом будет ошибка
  `100: One of the parameters specified was missing or invalid` — именно так
  вызовы терялись до 1.122.0.

Отчёт о доставке каждого вызова пишется в `alerts/<id>/delivery`
(`by` — `client` или `server`; `channels` — `sent` / `not_configured` /
`error: …` по каждому приёмнику; `configured`, `sent`, `push` — число
подписок админов, `at`). Панель «Вызовы 🚨» показывает его под каждым вызовом
(`📡 Доставка из браузера: …` / `📡 Серверная доставка: …`); пропущенные
вызовы получают `skipped: 'notifications_disabled'`, `'rate_limited'` или
`'server_mode'`.

Отчёт браузера пишет сам игрок, поэтому правило `alerts/$id/delivery/.write`
разрешает запись админу, автору вызова (`createdBy` — его добавляет
`requestOfficialCall`, потому что в QR-сессии `playerId` — это игрок, а
`auth.uid` — анонимная сессия устройства) и самому игроку. Запись
best-effort и через `update()`: если правила не задеплоены, доставка всё
равно выполняется, а серверный leaf `delivery/push` не затирается.
Отсутствие отчёта в режиме `client` чаще всего означает, что
`firebase deploy --only database` не выполняли.

Проверить боевой путь, не выходя на поле:

- режим `client` — кнопки **«Проверить Группу»**, **«Проверить Канал»** и
  **«Проверить отправку в ВК»**: они идут тем же кодом, что и настоящий вызов;
- режим `server` — админка → **Вызовы 🚨 → «Проверить серверную доставку»**.
  Кнопка вызывает callable `testOfficialCallDelivery` (только админ/мастер),
  который прогоняет тот же `deliverOfficialCall()` и возвращает отчёт по
  каналам.

## Диагностика

- На клиенте: `Notification.permission === 'granted'`,
  вкладка Application → Service Workers → Push (тестовая отправка в
  Chrome DevTools);
- подписка видна в базе `/push_subscriptions`;
- логи функции: `firebase functions:log -n onBroadcastCreated` /
  `-n onAlertCreated` — строка `alert push: N admin subs of M` показывает,
  сколько подписок админов найдено из общего числа; N = 0 означает, что у
  аккаунта, открывшего админку, нет ни `admin: true`, ни `role: 'admin'`;
- Telegram/VK: в админке у каждого вызова есть строка
  `📡 Доставка из браузера` или `📡 Серверная доставка` со статусом каждого
  приёмника — это первичный источник правды в обоих режимах;
- в режиме `server` дополнительно `firebase functions:log -n onAlertCreated`:
  строка `onAlertCreated: delivered via telegram:group, vk` при успехе,
  `nothing delivered` с JSON-ом причин при отказе и
  `delivery mode = client, channels skipped`, когда рассылает браузер;
- мёртвые подписки (404/410) функция удаляет автоматически.
