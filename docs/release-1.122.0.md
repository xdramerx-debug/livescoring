# Версия 1.122.0 — вызов судьи и маршала доходит до Telegram и ВКонтакте

Тестовые сообщения из админки приходили и в Telegram, и в ВК, а настоящий вызов
судьи или маршала во время раунда — нет. Причина в том, что «проверка
соединения» и боевая отправка идут **разными путями**, и до этой версии второй
путь никто не проверял:

| | Кто отправляет | Откуда токен | Что доказывает |
|---|---|---|---|
| «Проверить Группу / Канал / ВК» | браузер админа (`fetch` / JSONP) | значение поля ввода | токен и chat ID верны |
| Вызов во время раунда | Cloud Function `onAlertCreated` | ветка `channels/` через Admin SDK | — (ничего не показывало) |

То есть зелёный тест не означал ничего, кроме «токен рабочий». Ниже — три
конкретных дефекта серверного пути и отсутствие обратной связи, из-за которого
их нельзя было заметить.

## 1. ВКонтакте: сервер слал JSON-тело, а VK API его не понимает

`deliverOfficialCall()` в `functions/index.js` отправлял `messages.send`
через `channelPostJson()` — `Content-Type: application/json` с параметрами
в теле. VK API так не работает: поддерживаются query-строка и
`application/x-www-form-urlencoded`, а «значение `application/json`
в настоящее время не поддерживается»
(<https://dev.vk.com/ru/api/api-requests>). Ответом была ошибка
`100: One of the parameters specified was missing or invalid`, функция писала
`vk send failed` в лог — и на этом всё: в беседе ВК тишина.

Браузерный тест при этом проходил, потому что шлёт JSONP-ом с параметрами
в URL (`vkSendMessageJsonp`, `v=5.199`) — совсем другой формат запроса.

Что сделано:

- добавлен `channelPostForm()` — тело `x-www-form-urlencoded` из
  `URLSearchParams`; `messages.send` вызывается только через него;
- ответ сначала читается текстом и только потом парсится: на 502 от прокси
  или HTML-странице ошибки `res.json()` бросал исключение, и в логе оставалось
  «Unexpected token <» вместо настоящей причины;
- ошибка VK разбирается в `code N: сообщение` и попадает в отчёт доставки.

## 2. Telegram: сервер требовал ровно те имена полей, что пишет новая админка

Доставка в группу срабатывала только при `channels/telegram.groupToken` **и**
`groupId`, в канал — только при `channelToken` **и** `channelId`. Но:

- `migrateLegacyChannelSecrets()` при переносе секретов из публичного
  `/settings` пишет и старую пару `botToken`/`chatId` — если перенос прошёл
  только для неё, сервер не находил ничего и молча не отправлял;
- подсказка в админке разрешает «использовать один и тот же бот» для группы и
  канала, но при пустом `channelToken` канал не получал ничего, хотя ID задан;
- `peer_id`, сохранённый числом (`input type="number"`), отбрасывался
  серверным `str()`, который принимает только строки.

Что сделано: `normalizeChannelSettings()` приводит ветку `channels/` к рабочему
виду с теми же фолбэками, что и клиентская загрузка настроек
(`groupToken || botToken`, `groupId || chatId`, токен группы для канала при
заданном `channelId`), и понимает числовой `peer_id`. Сервер больше не строже
админки.

## 3. Пустое поле токена затирало сохранённый токен

`loadTelegramSettings()` сначала очищает поля, а значения приходят из
`channels/` асинхронно. Кнопка «Сохранить Группу», нажатая до их прихода (или
когда чтение ветки не удалось), записывала `channelToken: ''` и `channelId: ''`
— рабочий канал исчезал из базы. Тест продолжал присылать сообщение
(значение из поля), а вызовы с поля идти переставали.

Что сделано: `saveTelegramSettings()` читает сохранённое и сливает — пустое
поле оставляет прежнее значение, а тост сообщает, какие поля взяты из базы.
Заодно ошибки записи в `channels/` больше не проглатываются: раньше
`.catch(function(){})` стоял и в `saveTelegramSettings`, и во всех трёх
«проверить» — то есть токен мог не сохраниться вообще, а админ увидел бы
только «✅ Сообщение доставлено».

## 4. Доставку стало видно

Главное, чего не хватало: серверный путь не оставлял следов. Теперь:

- `onAlertCreated` пишет отчёт в `alerts/<id>/delivery`
  (`channels`, `configured`, `sent`, `push`, `at`), а пропущенные вызовы —
  с причиной (`notifications_disabled`, `rate_limited`). Панель «Вызовы 🚨»
  показывает его под каждым вызовом: `📡 Серверная доставка: Telegram (группа
  судей) ✅ · ВКонтакте ❌ code 100: … · push: 2 админ.` Отсутствие отчёта —
  признак того, что функция не сработала вовсе;
- новая кнопка **«Проверить серверную доставку»** (вкладка «Вызовы») дёргает
  callable `testOfficialCallDelivery` — он прогоняет тот же
  `deliverOfficialCall()` и возвращает отчёт по каждому каналу. Незадеплоенная
  функция распознаётся и объясняется командой деплоя; выключенные глобально
  уведомления — тоже;
- антиспам-ключ стал `раунд + игрок + тип` вместо одного раунда: раньше второй
  вызов из того же флайта в течение 2 секунд отбрасывался целиком и в
  Telegram/ВК не уходил вообще.

Секреты при этом остались на сервере: `channels/` читается только Admin SDK,
браузер игрока токенов не видит (docs/CODE-AUDIT-2026-10-2.md, находка 1).

## Что проверить после деплоя

1. `cd functions && npm i && firebase deploy --only functions` — правки
   в `functions/index.js` (доставка + новый callable).
2. `firebase deploy --only database` — правила не менялись, но деплой сайта
   (`--only hosting`) нужен ради админки.
3. В админке: **Вызовы 🚨 → «Проверить серверную доставку»**. Ожидаемый ответ —
   `✅ Серверная доставка работает` и список каналов. Если
   `❌ Cloud Function … не задеплоена` — см. шаг 1.
4. Сделать вызов судьи с лунки и посмотреть в панели «Вызовы» строку
   `📡 Серверная доставка` у этого вызова.
5. В логах: `firebase functions:log -n onAlertCreated` — строка
   `onAlertCreated: delivered via telegram:group, vk`. Строка
   `nothing delivered` сопровождается JSON-ом причин.

## Проверки

- новый `tools/test-official-delivery.js` (112 проверок): VK отправляется
  form-urlencoded и никогда JSON-ом; `peer_id`, `access_token`, `v`,
  `random_id` и текст без HTML-разметки в теле; legacy `botToken`/`chatId` и
  числовой `peer_id` принимаются; один бот на группу и канал; пустые
  `channels/` дают `not_configured` без единого внешнего запроса; ошибка или
  обрыв сети одного канала не отменяет остальные и попадает в отчёт; не-JSON
  ответ не роняет функцию; отчёт пишется в `alerts/<id>/delivery`;
  антиспам-ключ — игрок+тип; callable требует админа; админка не затирает токен
  пустым полем и не проглатывает ошибки записи. Плюс поведение админки в jsdom:
  слияние при сохранении, отчёт серверной проверки по каждому приёмнику,
  инструкция при незадеплоенной функции, экранирование причины отказа,
  пришедшей с сервера. На коде 1.121.0 тест падает (22 провала) — ровно на
  сценариях этой версии;
- `tools/test-channels-secrets.js` и `tools/test-functions-push.js` — без
  изменений, зелёные: токены по-прежнему не читаются из `/settings` и не
  отправляются из браузера;
- `tools/test-i18n-coverage.js` — новые ключи (`srv_delivery_*`,
  `vk_delivery_note`) есть в ru и en, в `js/i18n.js` и `src/i18n.js`;
- `npm test` — весь набор зелёный, `npm run lint` — чисто,
  `npm run assets` — версии статики и precache обновлены.
