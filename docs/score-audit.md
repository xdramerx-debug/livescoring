# Серверный журнал счёта

Журнал доступен во вкладке «Журнал счёта» в админке: ФИО/ID, дата **серверного подтверждения** (в часовом поясе браузера), лунка, старое/новое значение, тип ввода, оператор. Для офлайн-ввода с задержкой больше минуты показано также время нажатия на устройстве — оно не удостоверяется сервером. Кнопка «Все 30 дней» ищет по всем разделам последних 30 дней; при большом числе записей показаны первые 1000 результатов.

`scoreWrite`/`studioScoreWrite` проверяют полномочия на сервере; транзакция RTDB атомарно сохраняет новое значение и outbox аудита в раунде/турнире. Только после доставки события в защищённый `/scoreAudit/{UTC-день}` callable подтверждает успех. Вспомогательные onCreate-триггеры и плановая задача повторяют доставку после прерывания. Идемпотентный `requestId` сохраняется в локальной офлайн-очереди; последовательное воспроизведение не схлопывает исправления одной лунки. Если связь пропала, счёт не помечается как серверно подтверждённый: статус очереди виден в интерфейсе, после восстановления требуется ответ callable. Очередь хранится только **на этом устройстве** в localStorage; не очищайте данные браузера до синхронизации. Операции с безвозвратно отклонёнными полномочиями остаются в очереди, пока оператор не исправит доступ. Для личных записей после переключения аккаунта нужно войти в исходный аккаунт.

QR-карточка не требует **личного** входа. Для чтения раунда правилами RTDB нужна техническая Firebase Auth-сессия: в Firebase Console → Authentication → Sign-in method необходимо **включить Anonymous**. Открывающий QR под другим личным аккаунтом всё равно фиксируется как «QR-доступ, личность не подтверждена». QR-ссылка не является доказательством личности; выдавайте её адресно. Запись по мастер-паролю помечена как «Мастер-пароль (оператор не установлен)», поскольку пароль общий.

Хранение: плановая задача `purgeScoreAudit` в 03:00 UTC удаляет события старше 30 суток, включая пограничный день, а также ключи идемпотентности этих записей. Поэтому фактическая физическая задержка удаления после достижения 30 суток составляет до 24 часов. Интерфейс скрывает события старше 30 суток сразу. Исходный офлайн-тап может быть старше 30 суток: срок хранения события считается от серверного подтверждения. В Firebase нужен тариф/права для Cloud Functions и Cloud Scheduler.

**Ограничение действующей схемы:** унаследованные RTDB `.write` на узлах раунда и турнира, а также правила удаления позволяют устаревшим/внешним клиентам напрямую менять или удалять значения в обход callable. Отдельные `onWrite`-триггеры отмечают такие изменения как `legacy_direct_write` с неподтверждённой атрибуцией **после записи**, но не могут гарантировать их блокирование или атомарность с журналом. Для строгой невозможности обхода нужна миграция старой схемы разрешений и всех клиентских путей изменения раунда/турнира на сервер (или вынос счёта в отдельный защищённый узел). Не представляйте резервные триггеры как доказательство личности или абсолютную гарантию для прямых записей.

Перед вводом в эксплуатацию: `npm run test:ci && npm run lint:syntax && npm run assets && npm run build`; включить Anonymous Auth; настроить секрет мастер-пароля (см. `docs/tournament-master-access.md`); развернуть **functions, database, hosting одновременно** (`firebase deploy --only functions,database,hosting --project livescore-b77e4`). Не выкладывать только hosting: новые клиенты требуют callable и обновлённых правил. После деплоя вручную проверить один QR-раунд без личного входа и без сети, исправление счёта и фильтрацию журнала.
